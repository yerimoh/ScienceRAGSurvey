# Retrieval-Augmented Question Answering over Scientific Literature for the Electron-Ion Collider

> arXiv:2604.02259 | 2026 | Method | physics
> Ramaiah University of Applied Sciences (India) + College of William & Mary (USA)
> Follow-up work: extends AI4EIC's RAGS4EIC (arXiv:2403.15729) with a local LLaMA

## TL;DR
A RAG Q&A system that builds an in-house vector database indexing **178 EIC-related arXiv papers** and generates answers with **LLaMA 3.2** (open-source, locally deployed). Evaluated on **AI4EIC2023_DATASETS 51Q**, achieving **Context Recall ~1.0, with the chunk 180 · MMR combination giving the best performance**. Removes proprietary-model dependence and the risk of transmitting the KB to the cloud.

## Background
**Limitations of the existing approach (RAGS4EIC, arXiv:2403.15729)**
- Dependence on **proprietary models** such as GPT-4 + a **cloud-hosted** external KB → risk of transmitting unpublished EIC data externally
- High cost and internet dependence make it unusable in resource-constrained environments
- Reliance on a proprietary tokenizer → limits domain-specific fine-tuning

**Why this system was needed**
- "EIC is a multi-continental, multi-institutional project" (190+ institutes) → privacy-first is essential
- Prevents external exposure of unpublished, pre-release materials
- A cost-efficient solution so that resource-constrained institutions can also deploy it

## Construction Methodology

```
Step 1 — Building the Knowledge Base
  Collected 178 EIC-related papers from the arXiv preprint repository
  Domains: phenomenology, software, detector, accelerator physics
  Concatenate metadata (arXiv ID, authors, year) into the chunk
  → semantic chunk-source disambiguation

Step 2 — Chunking & Embedding
  LangChain RecursiveCharacterTextSplitter:
    chunk size 120 or 180 chars, overlap = 20 chars
  Embedding: mxbai-embed-large (Mixedbread AI, 1024-dim, strong on MTEB)
  Local deployment, no API dependency

Step 3 — Vector Database
  Chose ChromaDB (after comparing FAISS · Pinecone · LanceDB)
    - Can be deployed locally
    - Integrates smoothly with LangChain orchestration

Step 4 — Retrieval
  Query → 1024-dim vector (same mxbai-embed-large)
  Retrieve Top-20 chunks
  Similarity:
    ┌─ Cosine similarity (angle-based)
    └─ MMR (Maximum Marginal Relevance) — relevance × diversity

Step 5 — Generation
  Top-20 chunks → prompt template → LLaMA 3.2 or 3.3 (on-premise)
  guardrail: "answer only from provided context"
  citation tracing: track arXiv ID with LangSmith

Step 6 — Evaluation (RAGAS framework, 6 metrics)
  Benchmark: AI4EIC2023_DATASETS (51Q × N claims)
  4-way combination evaluation: chunk{120,180} × sim{cosine,MMR}
```

## Input
- 178 arXiv papers (chunked, embedded into ChromaDB)
- User natural-language query
- Retrieval strategy: cosine sim or MMR, top-20

## Output
- Answer generated by LLaMA 3.2 + LangSmith-traced arXiv citation
- RAGAS 6-metric (Faithfulness, Answer Relevancy, Answer Correctness, Context Entity Recall, Context Recall, Context Precision)

## Example questions (cited from the paper's Section 4.1 benchmark text)

### 📘 Evaluation dataset structure (verbatim from the text)
> "The AI4EIC2023_DATASETS is the high quality benchmark dataset that contains the ground truth answers of a set of **51 questions** ... Each question in this dataset is mapped to a pre-defined number of sub-parts called 'claims', individual answer against each claim and a comprehensive answer of the entire question. The AI-generated QA-pairs are meticulously vetted by human experts to create a gold-truth."

### 📘 Domain scope
> "These ground truth question-answers are generated using GPT-4.0 model, contextualized from the EIC-related publications from the arXiv pre-print repository across domains e.g., high energy phenomenology (hep.ph), nuclear experiments (nucl.ex) etc."

### 📘 Knowledge Base composition (Sec. 3)
> "The knowledge base of this RAG-inspired Q&A application is constructed with **178 EIC-related research articles** from the arXiv preprint repository. These scholarly articles span research domains across phenomenology, software development, detector design, accelerator physics etc."

### 📘 Chunking philosophy (author quote)
> "smaller chunks may increase precision but risk missing essential information, while larger chunks capture more content but may compromise relevance"

> This paper does not quote any specific question sentence verbatim among the 51 Q. The full 51Q can be found in the AI4EIC2023_DATASETS GitHub repository. (See the preceding paper arXiv:2403.15729)

## Main evaluation results (Sec. 4.2)

**Retrieval Latency (Fig. 2, median)**

| Setting | Latency |
|---|---|
| chunk 120 | 0.11 s |
| chunk 180 | 0.11–0.12 s |
| Cosine vs MMR | not significant (no difference) |

**Inference Latency (Fig. 3) — the LLM choice is decisive**

| LLM | Latency (median) | Note |
|---|---|---|
| **LLaMA 3.2** | **10–20 s** | stable, narrow IQR, outliers 50–60s |
| LLaMA 3.3 | much larger | more compute, many extreme outliers |

> Author conclusion: **"LLaMA 3.3 model utilizes more compute and exhibits substantially higher and more varying latency ... we incorporated the LLaMA 3.2 model for further study."**

**RAGAS Metrics (Fig. 4 · 5, 4-way combination distribution)**

| Metric | Observation |
|---|---|
| **Context Recall** | clustering ≈ 1.0 (improved especially at chunk 180) |
| Faithfulness | high-skewed at chunk 180 (good) |
| Context Precision | bimodal: [0.1, 0.3] vs [0.8+] |
| **Context Entity Recall** | low–moderate, **weak point** ← limits of domain entity extraction |
| Answer Relevancy / Correctness | most stable in the chunk 180 + MMR combination |

> Author analysis: **"the dense embedding models are optimized for general semantic not for any specific scientific terminology"** → scientific named entity recall is a weak point

## Limitations (stated by the authors)
- Limited to 178 arXiv papers — internal institutional documents, reports, and detector specifications are not included
- **Low Context Entity Recall**: general embedding models handle EIC-domain named entities (detector codes, particle symbols, etc.) poorly
- LLaMA 3.3 is unusable due to latency blow-up → reverted to LLaMA 3.2
- Evaluation is limited to the GPT-4-generated 51Q; a human-curated, diverse benchmark is lacking
- Planned upgrade of the pipeline to LangGraph (currently LangChain)
