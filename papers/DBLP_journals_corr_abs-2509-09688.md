# AI-Powered Assistant for Long-Term Access to RHIC Knowledge

> arXiv 2509.09688 | 2025 | Method | physics
> Brookhaven National Laboratory (STAR / PHENIX / sPHENIX / RHIC DAPP)

## TL;DR
To permanently preserve the **~1 EB of data + 600+ papers + tacit knowledge such as mailing lists** accumulated over 25 years of operation at Brookhaven's RHIC accelerator, the authors build an **MCP (Model Context Protocol)-based RAG assistant** (DAPP). It sets up on-premise infrastructure with ChromaDB + vLLM/Llama3.3, Mistral-Large, and LlamaCpp/Ollama, and can even cite private internal mailing lists.

## Background
**Limitations of existing approaches**
- The STAR/PHENIX/sPHENIX experimental know-how accumulated by RHIC over 25 years is scattered across dispersed forms such as internal mailing lists, technical notes, and legacy PostScript files, putting it at risk of being lost
- Commercial LLMs such as ChatGPT/Gemini/Claude are trained only on public data → they cannot access private internal context (debugging records, operations notes, etc.)
- Because of tiered collaboration policies (public / collaboration-restricted / controlled), a single cloud SaaS cannot be used

**Why this system was needed**
- A need to solve the temporal problem that "today's graduate student may have to understand a methodology developed 20 years ago"
- To transfer knowledge to the **follow-up EIC (Electron-Ion Collider) experiment** in line with the end of RHIC operation in 2025
- To provide a natural-language queryable interface without exposing pre-publication internal materials externally

## How It Was Built (Construction Methodology)

```
Step 1 — Recursive Multi-Format Web-Content Extraction (Fig. 2.1)
  Seed URL → traverse HTML with BeautifulSoup + requests
  dynamic filter / blacklist (block calendars, login pages)
  dedicated parser per file extension:
  ┌─ HTML       : remove nav → parse body + hyperlinks
  ├─ PDF        : Marker (ML-based PDF→Markdown)
  ├─ DOC/PPT    : LibreOffice conversion
  └─ PS/EPS     : convert to PDF with Ghostscript, then Marker

Step 2 — Text cleaning + metadata header attachment
  add source URL, page title, timestamp
  statistics logging (redirect/filter/extension frequency)

Step 3 — Vector embedding (ChromaDB)
  RHIC technical notes · conference slides · code snippets · SW documentation
  embedded into searchable ChromaDB

Step 4 — MCP orchestration (FastAPI-MCP)
  attach JSON header to the /ask request:
    - ordered stack of models
    - max context budget per stage
    - security tier (based on caller credentials)
  per-stage context separation: retrieval → summarization
                       → inference → evaluation
  routing per security tier (public/collaboration-restricted/controlled)

Step 5 — Multi-engine inference comparison (Fig. 3.1)
  vLLM      : ↑ multi-GPU throughput, maintains 80%+ utilization
  LlamaCpp  : ↑ 1-GPU throughput, drops sharply to 21% utilization on 4-GPU
  Ollama    : both throughput and utilization decrease as GPU count increases
  HW: throughput scales in order A6000 → A100 → H100
```

## Input
- **Collection targets**: RHIC internal collaboration website, archives, mailing lists (HTML/PDF/PS/DOCX/PPTX)
- **User query**: natural language (`/ask` endpoint)
- **Security context**: SSO authentication, RBAC, data classification (public / collaboration-restricted / controlled)

## Output
- Responses generated by the LLM using the retrieved context (comparison of Llama3.3-70B / Mistral-Large-2411 / ChatGPT o3)
- Citations of source documents (mailing lists / arXiv / internal technical notes)
- Future: AES-256 at rest, TLS 1.3 in transit, audit log

## Example Questions (directly quoted from Section 4. Benchmarking of the paper body)

This system is evaluated with internal benchmark queries written by STAR experts. Two verbatim Qs stated in the body:

### 📘 STAR Detector Operations Query ①
> **Q**: "How are space charge effects considered in the STAR experiment?"
> **Evaluation method**: qualitative comparison of the LLM response against a ground-truth answer written by domain experts

### 📘 STAR Detector Operations Query ②
> **Q**: "What is the TOF resolution in STAR experiment?"
> **Evaluation method**: same (expert reference vs LLM generation)

### 📘 Evaluation System Comparison (verbatim from the body)
> "Llama3.3 model was noted for its concise and detailed narrative, whereas Mistral was similarly precise but slightly more verbose. In contrast, ChatGPT o3 adopted a more pedagogical, verbose style that, while comprehensive, included extraneous details."
>
> "Llama3.3 and Mistral models successfully and quickly retrieved context from internal collaboration mailing lists, which are inaccessible to public-facing commercial LLMs."

## Key Evaluation Results

**LLM comparison (qualitative evaluation, body Section 4)**

| LLM | Runtime environment | Key evaluation result |
|---|---|---|
| **Llama3.3-70B + RAG** | local vLLM | accurate & concise, **successfully cited internal mailing lists** |
| **Mistral-Large-2411 + RAG** | local | accurate but slightly verbose |
| ChatGPT o3 (baseline) | commercial SaaS | cited **only public materials** such as arXiv / ResearchGate, no access to internal debugging records |

**Inference engine throughput (Fig. 3.1, quantitative)**

| Engine | 1-GPU throughput | 4-GPU utilization | Design philosophy |
|---|---|---|---|
| vLLM | medium | **maintains >80%** | parallel-first |
| LlamaCpp | **highest** | drops sharply to 21% | memory distribution-first |
| Ollama | medium | gradual decrease | balanced |

> By HW generation: H100 > A100 > A6000 (common across all engines)

## Key Contributions
1. **Integrates private mailing lists + informal discussions, which public chatbots cannot access, into the LLM knowledge base**
2. **Adoption of MCP**: separates the retrieval, summarization, inference, and evaluation stages into independent contexts → ↑ monitoring and explainability
3. **3-engine benchmark**: quantitative comparison of vLLM/LlamaCpp/Ollama throughput and utilization (Fig. 3.1)
4. Presents a **STAR use case → template generalizable to EIC**

## Limitations
- Evaluation is mostly **qualitative comparison**, lacking quantitative IR metrics (P@k, MRR)
- Public / collaboration-restricted / controlled permission separation and full RBAC implementation are in progress
- Automatic synchronization of external latest publications (API, RSS feed) ↔ local DB is not implemented
- The size of the insider-level question set used for evaluation is undisclosed
