# Clinfo.ai: Open-Source RAG System for Medical QA over Scientific Literature
> PSB 2024 | Method | medical

## TL;DR
Clinfo.ai is the first publicly available open-source, end-to-end retrieval-augmented LLM (RetA LLM) system that takes a clinical question as input, dynamically searches the scientific literature on PubMed (or Semantic Scholar), selects and summarizes only the relevant abstracts, and then generates an evidence-grounded answer with numbered citations. Structured as four LLM modules connected into a single "LLM chain" and coupled to an external search index (Entrez API), it leverages the zero-shot reasoning ability of GPT-3.5/GPT-4 through prompting alone, without any fine-tuning.

## Architecture (Clinfo.ai Architecture)
Clinfo.ai consists of an **LLM chain in which four LLMs cooperate**, coupled to a search index (PubMed or Semantic Scholar) (Figure 2). All LLM stages use OpenAI's GPT-3.5 (`gpt-3.5-turbo-0613`) and GPT-4 (`gpt-4-0613`) snapshots, exchanging prompts through the LangChain API. As common settings, a temperature of 0.5 and a maximum of 1024 generated tokens are used. All stage-by-stage prompts are made public in the supplementary material (GitHub `SupplementalMaterial`).

- **(1) Query Generator (Question2Query)**: Takes the question submitted by the user and generates a PubMed (or Semantic Scholar) query capable of retrieving many relevant papers. The LLM is instructed to include the most essential and highly relevant keywords that accurately represent the context and requirements of the question. It is designed to emphasize recall over precision so as to pull in as many potentially relevant papers as possible.
- **(2) Search Index / Information Retriever (PubMed/Semantic Scholar, Entrez API)**: Sends the query built by the Query Generator to the NCBI Entrez (E-utilities) API to programmatically retrieve PubMed abstracts. Because the LLM output is stochastic and each query may capture a different aspect of the literature, the system takes the **union** of the papers returned by **3 LLM queries generated by applying different seeds to the same prompt**.
- **(3) Relevance Classifier**: Because the Query Generator prioritizes recall, a stage that judges the relevance of the retrieved papers is essential. Using GPT-3.5, each paper is judged for the question with a **binary classification** of relevant / not relevant. Papers judged relevant are used to construct **IEEE-format citations** by leveraging the full abstract metadata. If the relevant papers exceed 35, the user can re-rank and filter them with BM25.
- **(4) Summarizer / Synthesis**: Split into two LLM stages. First, **Summarization** individually summarizes each abstract judged relevant within the context of the user's question. Then **Synthesis** bundles the individual summaries into a numbered ordered list (each number corresponding to one citation), passes it to the LLM, and has it generate a concise and informative comprehensive summary. Here, the LLM is instructed to **use only the provided paper summaries and no other information**, and to accurately attribute each finding to its source through the citation list (numbered-citation grounding).

## Pipeline (inference)
When a single clinical question is input, it is processed in the following order.

1. **Question input**: The user submits a clinical question to the WebApp (e.g., "Does high-grade dysplasia/carcinoma in situ of the biliary duct margin affect the prognosis of extrahepatic cholangiocarcinoma?").
2. **Query generation**: The Question2Query module converts the question into a PubMed query. It generates 3 queries using the same prompt with different seeds (Figure 3 shows examples of actual generated queries).
3. **PubMed search**: Retrieves the union of the abstracts returned by the 3 queries via the Entrez API (in the example screen, 16 papers are retrieved).
4. **Relevant abstract selection**: The Relevance Classifier (GPT-3.5) binary-classifies each retrieved paper as relevant / not relevant. Relevant papers are constructed into IEEE-format citations, and if there are more than 35, a BM25 re-ranking option is provided.
5. **Individual evidence summarization**: In the Summarization stage, each relevant abstract is summarized to fit the question context.
6. **Synthesis + TL;DR output**: The Synthesis stage synthesizes the individual summaries into a **"Literature Summary" (= Synthesis)** with numbered citations, and also presents a **"TL;DR"** that compresses this into 1-2 sentences. The references are displayed as hyperlinks so the user can directly verify the validity of the citations and the extracted information (Figure 5). Even though an abstract was summarized, that paper may not be included in the final Literature Summary or TL;DR, but all relevant papers are exposed to the user.

The WebApp (www.clinfo.ai) supports selection of the search engine (PubMed, etc.) and prompt customization, and shows the generated queries, the number of retrieved papers, the individual summaries, and the final answer in real time.

## Evaluation (important)
The task is defined in **three stages**: (1) generating a query from the question and retrieving papers, (2) judging the relevance of the retrieved papers, and (3) summarizing the findings of the relevant papers.

- **Precision/recall applied only to Retrieval (stage 2)**: Letting RET(D,k) be the set of k documents retrieved and judged relevant, and REL(D,q) be the set of documents referenced by the SR, precision = |RET∩REL|/|RET| and recall = |RET∩REL|/|REL| are defined. **Precision/recall are not used for evaluating summary quality.**
- **Summarization (stage 3) is evaluated with summary-quality metrics**: The Source-Augmented (SA) metrics use UniEval (T5-large), COMET (XLM-RoBERTa), and CTC Summary Consistency (BERT), additionally referencing a context that concatenates the SR's introduction, results, and conclusion. The Source-Free (SF) metrics use BERTScore, ROUGE-L, METEOR, chrF, GoogleBLEU, CTC Summary (context not provided), and CharacTer to compare against human-curated gold-standard summaries. UniEval measures 4 dimensions — Coherence / Consistency / Fluency / Relevance — and their average (Overall).
- **Three evaluation regimes**: To control for the possibility that a new discovery is subsequently published and changes the answer — **Restricted Search (RS)**: retrieval is allowed only for papers up to one day before publication / **Source Dropped (SD)**: papers both before and after publication are retrieved, but the source SR itself is removed from the relevant set / **Unrestricted Search (US)**: no restriction (the source SR may be included; closed-form tools such as Elicit and Statpearls effectively operate in this regime). Questions that yield 0 hits under SD were excluded across all regimes, comparing 146 questions (time-unconstrained).
- **Verified figures (UniEval Overall, Unrestricted Search basis)**: Clinfo.ai TL;DR = 0.88, Synthesis & TL;DR = 0.84, Synthesis = 0.809. Non-augmented baselines GPT-3.5 = 0.872, GPT-4 = 0.86. Deployed tools Elicit = 0.713, Statpearls SS = 0.728. Clinfo.ai had a higher UniEval Overall than other RetA systems across all output strategies and all regimes, with the improvement reported as **at least 6.2% and at most 14.9%**.
- **Retrieval precision/recall (Table 3)**: Restricted Search precision 0.224 / recall 0.057, Source Dropped precision 0.186 / recall 0.064, Unrestricted Search precision 0.162 / recall 0.052 (the source SR was retrieved for 96.5% of questions, Source Included 0.965). Precision was highest under Restricted Search, where retrievable documents are limited. (Overall, adding RetA gives a slight improvement over the LLM on automatic metrics.)

## Jointly proposed benchmark: PubMedRS-200
PubMedRS-200 (PubMed Retrieval and Synthesis) is a public Open-QA dataset built on 200 systematic reviews (SRs). Using SRs as a proxy for queries of medical interest, questions were extracted from SRs whose titles are in question form, and two human annotators derived the answers from the results/conclusions. Each item includes a question, an answer, references (PubMed IDs), a context, and so on. (The detailed construction procedure is omitted from this summary.)

## Limitations
- **Absence of human evaluation**: Only automatic metrics, which show moderate-to-high correlation with human preference, were used, and the RetA LLM system was not directly evaluated by human preference. Future work should confirm the alignment with automatic metrics through human evaluation.
- **MeSH hallucination in query generation**: The LLM generally generates PubMed query syntax and Boolean operators well, but it may create **hallucinated (nonexistent) MeSH terms** and thereby miss relevant studies. Improving the reliability of the query-generation stage is a future task (directly tied to improving precision/recall).
- **Bias of automatic evaluation metrics**: SF metrics favor short responses and do not guarantee accuracy or comprehensiveness, while some SA metrics (UniEval Coherence/Relevance, COMET) prefer long generations. Because of the inconsistency among metrics, a fair performance evaluation is difficult.
- **Dependence on evaluation assumptions**: SA evaluation relies on the assumption that the system retrieves and synthesizes the papers the SR authors deemed relevant, so if this assumption breaks, the output may be excessively penalized.
