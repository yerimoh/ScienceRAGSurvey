MITRA: An AI Assistant for Knowledge Retrieval in Physics Collaborations

arXiv 2603.09800 | 2026 | Method | physics University of Wisconsin-Madison (CMS Collaboration) — NeurIPS 2025 ML4PS Workshop "MITRA" = Sanskrit "friend"

TL;DR

A RAG system that searches the vast internal analysis notes, wikis, and guidelines of the CERN CMS collaboration on-premise (NVIDIA Tesla T4, 15GB). It combines DPR + cross-encoder reranking + 4-bit Mistral-7B, and uses a 2-tier DB (abstracts → full-text) to prevent cross-analysis confusion. On semantic queries (Set 2), it improves P@1 by 5.8x over BM25 (0.13 → 0.75).

Background

Limitations of existing methods

  • CMS collaboration: thousands of members, several TB of analysis notes, internal wikis, and guidelines → manual keyword search is inefficient
  • Exact keyword matching such as BM25 cannot handle domain synonyms like "transverse momentum" ↔ "pT cut"
  • Using external LLM APIs (e.g., chATLAS's GPT-4o-mini) for unpublished analysis data raises privacy concerns
  • The cumulative API cost of a large collaboration is unreasonable compared to self-hosting
  • Handling multiple analyses (Higgs vs Dark Matter) in a single DB causes cross-analysis confusion

Why MITRA was needed

  • "the most important background" for a "Higgs→di-muon analysis" and for a "dark matter search" have different answers → context-aware DB separation is needed
  • semantic equivalence matters more than instance-level keywords in real-world use

Construction Methodology

Step 1 — Document collection (Offline)
  Selenium automation script → CMS internal DB login + PDF download
  OCR + layout parsing (Surya, Tesseract)
  Plain PyPDF/PDFPlumber not used (loss on complex layouts)
  chunking at paragraph granularity

Step 2 — Embedding (DPR)
  facebook/dpr-question_encoder-multiset-base
  → 768-dimensional vector
  stored in Chroma DB

Step 3 — 2-Tier vector DB structure
  ┌─ Abstracts DB    : abstracts of all analyses only
  └─ Full-Text DB    : chunked full text per analysis

  Query processing:
    1) first question → select the closest analysis from the Abstracts DB
    2) user confirms the analysis selection (human-in-the-loop)
    3) all subsequent questions → search only that analysis's Full-Text DB
       → prevents cross-analysis confusion

Step 4 — Reranking (Cross-Encoder)
  cross-encoder/ms-marco-MiniLM-L-6-v2
  Top-k (tunable) → rerank → sort

Step 5 — Generation (On-Premise)
  Mistral-7B 4-bit quantized (Ollama, LangChain)
  explicit prompt: "ground answers strictly within retrieved context"
  HW: NVIDIA Tesla T4 (15GB VRAM)
  UI: Streamlit

Step 6 — Evaluation (2 expert-designed query sets)
  Set 1: exact keyword phrasing
  Set 2: paraphrase / synonym (e.g., "transverse momentum requirement"
                                ↔ document's "pT cut")
  Baselines: BM25 (Okapi)
  Metrics: P@1/3/5, R@1/3/5, MRR, NDCG@3/5

Input

  • user natural-language question (Streamlit UI)
  • after selecting an analysis with the first query, the conversation locks on (session-bound context)

Output

  • retrieved passages + a cited answer generated by Mistral-7B
  • refusal capability for out-of-context questions (the authors ran a separate qualitative test)

Example items (verbatim quotes from the paper body)

📘 Cross-Analysis Confusion example (Sec. 3 body)

Q: "What is the most important background?"

Authors' analysis: "will have a different, and potentially conflicting, answer for a Higgs to di-muon analysis versus a search for dark matter" → resolved by locking on the analysis context with the 2-tier DB

📘 Set 2 Semantic Query (Sec. 4 body)

Q (user phrasing): "transverse momentum requirement"

expression in the document: "pT cut"

result: BM25 P@1 = 0.13, MITRA P@1 = 0.75 (5.8× improvement)

📘 Out-of-Context refusal (Sec. 4 qualitative-test body)

session context: locked on to a dark matter search analysis Q: "How many Higgs bosons were discovered in this search?" MITRA response (authors' quote): "it did not hallucinate an answer. Instead, it correctly inferred from the retrieved passages that the document was unrelated to Higgs bosons and informed the user that the analysis in question is a dark matter search."

Key evaluation results (Tables 1, 2)

Table 1 — Precision / Recall @k

Query Set System P@1 R@1 P@3 R@3 P@5 R@5
Set 1 (exact KW) BM25 1.00 0.85 0.40 0.90 0.32 1.00
Set 1 (exact KW) MITRA 1.00 0.85 0.40 0.90 0.24 0.90
Set 2 (semantic) BM25 0.13 0.03 0.25 0.56 0.18 0.59
Set 2 (semantic) MITRA 0.75 0.66 0.33 0.81 0.20 0.81

Table 2 — MRR / NDCG

Query Set System MRR NDCG@3 NDCG@5
Set 1 BM25 1.00 1.00 0.98
Set 1 MITRA 1.00 1.00 1.00
Set 2 BM25 0.35 0.67 0.59
Set 2 MITRA 0.81 0.91 0.88

Key insight: On Set 1 (exact keywords), BM25 = MITRA. On Set 2 (realistic paraphrases), MITRA dominates. The authors argue that "real users rarely know and search for the exact terminology of the source document."

Limitations (stated by the authors)

  • Prototype stage — before full CMS-collaboration deployment; planned expansion to multiple document types
  • The evaluation query set is small (2 expert-designed sets)
  • Only retrieval quality is measured; LLM-as-judge evaluation of the LLM answers' faithfulness/relevancy was not performed
  • Quantitative benchmarks of query latency and throughput are future work
  • Multi-turn conversation and migration to production with high-performance inference engines such as vLLM/llama.cpp are planned
  • Generalization to other physics collaborations (ATLAS's chATLAS, ALICE, etc.) is not validated
